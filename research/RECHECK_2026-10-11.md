## Уточнение вывода по V4

В [RESULTS_V4.md](https://github.com/ImmortalDR/CV_hakaton/blob/4f432a5c20679b7f2b92ef0c49720963408eecc6/dataset/training/RESULTS_V4.md) есть отдельный перспективный результат retrieval. По [исходному JSON](https://github.com/ImmortalDR/CV_hakaton/blob/4f432a5c20679b7f2b92ef0c49720963408eecc6/dataset/training/reports/v4-retrieval.json): E5 Recall@100 = 0.3792, TF-IDF = 0.2750; наблюдаемая разница +10.42 п.п. Но 95% интервал −12.93…+33.33 п.п. включает ноль, запросов только 15. Это не доказанное устойчивое превосходство.

[V4-CV](https://github.com/ImmortalDR/CV_hakaton/blob/4f432a5c20679b7f2b92ef0c49720963408eecc6/dataset/training/reports/v4-cv-training.json) выбрал char_cosine по OOF. Основная test NDCG@10 не определена: достаточно больших смешанных test-групп нет. Победитель на трёх малых группах не улучшил NDCG относительно word_cosine. Test уже просмотрен, а production_promotion_allowed=false. Прежний осторожный вывод о недоказанном персональном подборе сохраняется; прежний охват только V3/V3-CV был неполным.

Полезные идеи: честный baseline на том же допустимом пуле, разделение retrieval и ranking, неизвестный исход не считать отказом, явно отмечать недоступную основную метрику. Модели в LTN не включены.

## Дополнительное обновление 311 во время проверки

ae64cfa добавляет приватный backend, gateway token, фиксированный внешний HTTPS-origin и очистку недоверенных forwarding-заголовков. [Proxy guard](https://github.com/Hazernit/fsp-career-311/blob/ae64cfabb8eb310a0ffd2115338480dcc32fd4db/lib/server/proxy.ts) сохраняет исходный Origin для CSRF и восстанавливает внешнюю схему только после проверки токена. [Инструкция](https://github.com/Hazernit/fsp-career-311/blob/ae64cfabb8eb310a0ffd2115338480dcc32fd4db/deploy/YANDEX-CLOUD.md) явно отделяет локальный Wrangler-прогон от ещё не проверенной облачной сети/VM/Gateway. Это подготовка размещения, не доказательство опубликованного работающего стенда. В LTN облачное размещение не добавлялось; текущий локальный контейнер проверяется отдельно. При размещении FastAPI следует настроить доверенные прокси штатными средствами, не доверять произвольным заголовкам клиента.

## Что исправлено в собственной реализации

1. Ожидание автосохранения теперь проверяет стабильность всей очереди. Регрессия воспроизвела старую ошибку: ожидание заканчивалось, хотя добавленное сохранение ещё не завершилось. При смене роли поля ответов блокируются до перехода, при отказе восстанавливаются; повторный клик отключён.
2. Ответ HTTP 200 с невалидным JSON больше не принимается общим API-клиентом за успех. Раньше возвращался объект-заглушка detail, после которого вызывающий код мог очистить состояние.
3. Сравнение подбора исправлено: случайный порядок применяется к тому же допустимому пулу с устойчивым порядком ID и отдельным seed. NDCG@5 остаётся 0.9799, честный random baseline — 0.4991 вместо прежних 0.2117. Precision@5: 1.0000 против 0.8500. Прежняя разница смешивала фильтрацию категории и ранжирование.

Профили, потребности, метки, IRT-результаты и top IDs ранжирования структурно сверены и не менялись. Из входного JSON удалены только ранее встроенные вычисленные показатели; результаты вынесены отдельно. --check воспроизводит отчёт без записи и сравнивает его целиком; CI проверяет согласованность выводов с кодом и хешем входов. Эти показатели по-прежнему синтетические, не профессиональная валидация.
