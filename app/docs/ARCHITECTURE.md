# Архитектура

## Контур

```
Браузер: HTML + CSS + JavaScript
  ├── hash-маршруты двух кабинетов
  ├── fetch /api/* + cookie + X-CSRF-Token
  └── прямой защищённый экспорт PDF
              ↓
FastAPI (server.py)
  ├── роль, владелец записи, согласия
  ├── assessment.py: параметрические формы и EAP
  ├── matching.py: объяснимый индекс соответствия
  ├── ReportLab: PDF
  ├── SMTP: код регистрации, если настроен
  └── SQLite WAL: транзакции BEGIN IMMEDIATE
```

Один процесс и одна БД удобны для воспроизводимого локального запуска. Нет отдельного фронтенд-сервера, очереди, LLM и внешнего парсинга вакансий. Разделение доменной оценки на два небольших файла позволяет независимо проверить её математические свойства.

## Данные

`users` — роль, email, scrypt-хеш пароля, подтверждение, версия и состояние согласия. `profiles` и `companies` — формы соответствующей роли. `categories` — уникальная подтверждённая категория на `(user_id, spec)`. `sessions` — хеш случайного токена, CSRF и срок. `email_codes` — хеш одноразового кода, срок и счётчик ошибок.

`attempts` — приватные задания с ключами, публичная форма без ключей, ответы, версия, дедлайн и результат. Частичный уникальный индекс ограничивает одну активную попытку на участника. `needs` — критерии подбора и публикация. `invitations` — автор, адресат, содержание и состояние; уникальный индекс ограничивает одно открытое приглашение одной компании одному кандидату. `applications` — отклики с уникальностью по вакансии и кандидату. `grants` — отдельное разрешение компании на контакты, допускающее отзыв.

`tasks` — задания с категорией, темой и рубрикой. `assignments` — назначение и срок. `task_answers` — решение, ручной балл и комментарий. `notifications` — события пользователя. `audit` — значимые переходы, без паролей, кодов и содержимого контактов.

## Состояния

Попытка: `active → finished`, либо `active → expired` при старте следующей после дедлайна. После дедлайна редактирование ответов закрыто; активную попытку можно завершить с уже сохранёнными ответами. Незавершённая истекшая попытка не выдаёт категорию. Успех подтверждает выбранный уровень, неудача его не меняет. Переход грейда проверяется на старте; категория меняется после успешного результата.

Приглашение: `sent → viewed → accepted / declined`, либо `sent/viewed → withdrawn / expired`. Принятие требует `share_contacts=true`. Разрешение принадлежит паре компания–кандидат и проверяется при каждом чтении профиля и экспорте PDF. После отзыва разрешения повторный PATCH уже принятого приглашения его не восстанавливает; новое приглашение или новый самостоятельный отклик требует нового решения пользователя.

Задание: `assigned → submitted → reviewed`. Дубликат решения не принимается. Итог — `round(100 × сумма трёх критериев / 6)`, оценка публикуется кандидату. Проверка не переписывает категорию теста.

## Доступ и транзакции

- Пароли: scrypt с отдельной случайной солью; сравнение hmac.compare_digest.
- Cookie: HttpOnly, SameSite=Strict, 24 часа; Secure настраивается для HTTPS.
- Все изменяющие защищённые методы требуют CSRF-токен сеанса; браузерный Origin должен совпадать с адресом сервера.
- Параметризованный SQL. Выбор динамического имени колонки ограничен ролью из сервера, не строкой клиента.
- BEGIN IMMEDIATE сериализует операции изменения; версия попытки предотвращает запись устаревших ответов. Клиент отправляет полную актуальную карту ответов, чтобы последующий успешный save также восстанавливал ответы после временного сетевого сбоя.
- Проверяется владелец потребности, попытки, приглашения и проверяемого решения. Контакты не входят в неподтверждённые работодателем представления. Имя заменяется на номер профиля.
- Для публикации, чтения и выдачи контактов учитывается согласие обработки. Отзыв согласия завершает все сеансы и скрывает профиль.
- Ограничены попытки входа, регистрации, проверки и переотправки кода. Код почты живёт 15 минут, не более 5 ошибок.
- CSP разрешает только собственные скрипты. Тексты пользователя экранируются при рендеринге, PDF экранирует разметку. API-ответы имеют Cache-Control: no-store.

SQLite не заменяет промышленную многопроцессную БД: все чтения сейчас также используют транзакционный контекст, конкуренция сериализуется. Для роста нагрузки потребуется PostgreSQL, миграции, индексы под поиск, реальные фоновые задачи и отдельная политика хранения/удаления персональных данных. Нагрузочное тестирование и аудит безопасности не заявляются.

## ФСП

Организаторы не предоставили реальную схему и API. `REGISTRY` содержит шесть вымышленных ID, событие, дисциплину, результат, год, источник и экспертную силу сигнала. Связывание включает код владения; в демо он отображается в интерфейсе. При `FSP_DEMO=0` такая операция отключена. Для реального внедрения нужно заменить реестр и выдачу кода на согласованный процесс авторизации и верификации, а не открывать нынешний демо-адаптер как боевой.

Приложение не требует истории ФСП: нет достижений — вклад фактора 0.5, известные достижения добавляют ограниченный бонус. Пользователь может скрыть историю или отключить ID.
